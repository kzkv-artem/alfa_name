# Alfa Business Copilot — архитектура (этап 1: план)

Один ИИ-агент, два независимых раздела. Выбор раздела — на старте (меню), без LLM-роутинга.

## Общая схема

```
                    Alfa Business Copilot
                            │
              выбор раздела (2 пункта меню)
                    ┌───────┴───────┐
                    ▼               ▼
       Линия «Привлечение»   Линия «Продукт»
       Risk Advisor Agent      Product Router
                                     │
                        ┌────────────┼────────────┐
                        ▼            ▼             ▼
                  Кассовый      Гос поддержка   Страхование
                   разрыв        (alfa_gov_support.ipynb)    (новый)
                (alfa_cashflow.ipynb)
                    │            │             │
                    └────────────┴─────────────┘
                                 ▼
                 общий слой: LLM Gateway + Данные
```

Картинка — в сообщении выше (виджет `alfa_agent_architecture`).

## 1. Линия «Привлечение» — Risk Advisor Agent

Для тех, кто ещё не клиент/только присматривается к открытию бизнеса. Свободный чат: «хочу открыть бизнес X — какие риски».

- `market_signals` — синтетическая таблица (по аналогии с `alfa.csv`/`training_dataset.csv`): срез по отрасли × региону — кол-во ИП, динамика ИП г/г, средний оборот, процентиль оборота, доля закрытий за 12 мес, индекс лёгкости входа, сезонность.
- `RiskProfileBuilder` — детерминированный скоринг (без LLM): по (отрасль, регион, опц. бюджет) считает композитный риск-скор из сигналов выше.
- `RiskAdvisorAgent` — цикл диалога: LLM вытаскивает сущности из свободного текста → если не хватает данных, LLM сам формулирует уточняющий вопрос → RiskProfileBuilder считает цифры → LLM превращает структурные данные в связный ответ.

Открытый вопрос на потом: точная формула скоринга и конкретный список сигналов — договорим отдельно, когда дойдём до реализации.

## 2. Линия «Продукт» — три под-агента

Product Router — меню из трёх пунктов (кассовый разрыв / гос поддержка / страхование). Внутри каждого — обычный диалог с LLM.

### 2.1 Кассовый разрыв — перенесено в `alfa_agent/cashflow/`
ML-ядро и пороги перенесены из `alfa_cashflow.ipynb` без изменения логики:
- `db.py` — схема (`client`, `account`, `payment_transaction`, `recurring_pattern`, `forecast`), `connect()`.
- `ingest.py` — загрузка транзакций из `alfa.csv` (автоопределение разделителя/кодировки).
- `patterns.py` — детект регулярных платежей по коэффициенту вариации интервалов/сумм. При переносе нашли и починили риск: даты в БД хранятся как `24.03.2026` (день.месяц.год), `pandas` определял формат угадыванием — при неудачном наборе дат мог бы молча перепутать день и месяц. Зафиксировали формат явно.
- `model.py` — обучение CatBoost (`train_model`), сохранение/загрузка модели в `data/cashflow_model.cbm`, `python -m alfa_agent.cashflow.model` — переобучить и сохранить.
- `forecasting.py` — `run_forecast()`, тот же алгоритм скользящего баланса на 21 день вперёд.
- `agent.py` — `CashflowAgent`: `run()` — пороги алерта (уверенность, сумма, серьёзность) + короткое LLM-уведомление; `explain_in_detail()` — развёрнутое объяснение (шаблон `cashflow_explanation`, раньше был зарегистрирован, но не использовался).
- Демо: `otbor/try_cashflow_agent.py`.
- Проверено живыми вызовами модели на демо-клиенте и на сконструированном сценарии разрыва.

### 2.2 Гос поддержка — перенесено в `alfa_agent/gov_support/`
Правила подбора перенесены из `alfa_gov_support.ipynb` без изменения логики:
- `db.py` — `build_database()` пересобирает БД из `otbor/schema.sql`.
- `ingest.py` — загрузка мер поддержки из `mery-podderzhki-msp-2026.csv`.
- `normalize.py` — разбор уровня/типа/возраста/статуса/канала подачи в структурированные поля.
- `matching.py` — `check_eligibility`, `run_matching`, `missing_documents`, `available_documents` (новое — нужно для запроса документов), `decide`. Дата отсечки (`AS_OF`) теперь параметр, а не захардкоженная константа — раньше была жёстко зашита `"2026-07-19"`, что сломало бы расчёт возраста при реальном использовании позже этой даты.
- `agent.py` — `GovSupportAgent`: `advise()` — объяснение решения по программе; `draft_application()` — черновик заявления (отправляет только пользователь, кнопки «отправить» в бэкенде нет вообще); `request_documents()` — досюда не был подключён шаблон `documents_request`, теперь используется для случая «не хватает больше 2 документов».
- Демо: `otbor/try_gov_support_agent.py`.
- Проверено живыми вызовами модели на всех трёх ветках решения (подходит+черновик, не подходит, запрос документов).

### 2.3 Страхование (в работе)
Слои L0–L5 из ТЗ, реализовано пока L0–L3 (детерминированные, без LLM):
- `alfa_agent/insurance/catalog.py` — L0, 7 продуктов АльфаСтрахования (`TENANT`, `PROP_MSB`, `EQUIP`, `GL`, `PRODQ`, `DMS`, `CYBER`) из продуктовой матрицы: официальное/клиентское имя, от чего защищает человеческим языком, триггер, требуемые атрибуты, исключения, ориентир по стоимости (без выдумывания цены, если её нет в каталоге), ссылка/порядок оформления.
- `alfa_agent/insurance/features.py` — `ClientFeatures`, датакласс признаков клиента (что банк знает из транзакций и профиля).
- `alfa_agent/insurance/synthetic.py` — генератор синтетики: скрытые факты о бизнесе → транзакции с шумом → восстановленные признаки (двухслойная схема, метка считается из скрытых фактов, движок её не видит). 400 клиентов, 7 архетипов (бьюти/креатив/ритейл × самозанятый/ИП/ООО).
- `alfa_agent/insurance/scoring.py` — L1 `eligible()` (применимость), L2 `risk_exposure() × vulnerability()` = `need_score`, L3 `recommend()` → топ-3 с отсечкой 0.25. Перенесено из присланного эталонного `engine.py` и сверено с ним побитово на всех 400 клиентах — 0 расхождений.
- `alfa_agent/insurance/agent.py` — L4, `InsuranceAdvisorAgent`: `recommend_and_explain()` объясняет топ-3 человеческим языком (сценарий потери денег, почему именно этому клиенту, цена только если она есть в каталоге), при отсутствии предложений — тишина (`None`), это валидный результат; `answer_followup()` — уточняющий диалог по уже показанным продуктам, ответ строго по данным каталога, без выдумывания цифр. Проверено живым вызовом модели на нескольких сценариях (обычная рекомендация, тишина у самозанятого, продление у уже страхованного клиента).
- L5 (логирование откликов для дообучения) — не сделано, по желанию.

## 3. Общий слой

**LLM Gateway** — единая точка выхода в LLM для обеих линий:
- `LLMClient` — интерфейс `generate(system, user, **kwargs)`
- `DeepSeekClient` — реализация поверх OpenAI-совместимого SDK (DeepSeek API или OpenRouter, роутинг решаем на уровне base_url/ключа)
- `prompts.py` — реестр промпт-шаблонов по сценариям: `risk_chat`, `eligibility_explainer`, `application_draft`, `cashflow_alert`, `insurance_recommendation`
- Никакой бизнес-логики в промптах — только объяснение уже посчитанных данных

**Данные** — по одной SQLite-базе на агента (как сейчас): `cashflow_v2.db`, `gospodderzhka.db`, + новые `market_signals` (риск) и `insurance_catalog` (страхование).

```
alfa_agent/
  llm/

    prompts.py

  acquisition/

    agent.py
  insurance/
    catalog.py        # L0
    features.py        # L0
    synthetic.py        # L0, генератор синтетики
    scoring.py           # L1-L3
    agent.py               # L4 (в работе)
    feedback.py               # L5 (не сейчас)
  product/
    cashflow/
      forecasting.py   # из alfa_cashflow.ipynb
      agent.py
    gov_support/
      matching.py       # из alfa_gov_support.ipynb
      agent.py
    router.py
  common/
    db.py
    schemas.py
main.py                 # меню: раздел → линия
```

Фактическая структура `insurance/` лежит прямо в `alfa_agent/`, а не под `product/`, как было в первом черновике — так проще, `product/` пока не собран.

## Решения, зафиксированные на этом шаге
- LLM: облачный API, OpenAI-совместимый клиент (DeepSeek/OpenRouter)
- Данные для риск-линии: синтетика, генерим сами
- Роутинг: два раздела на старте, пользователь выбирает вручную
